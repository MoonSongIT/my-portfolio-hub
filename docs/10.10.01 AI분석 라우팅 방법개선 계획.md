# AI분석 라우팅 방법 개선 계획

_작성일: 2026-05-20_

---

## 1. 현행 라우팅의 구체적 문제

### 1-1. 라우팅 로직이 두 파일에 분산

`orchestrator.js`와 `AIChat.jsx` 양쪽에 라우팅 판단이 있어 동기화가 깨지기 쉽다.

```js
// AIChat.jsx L130-141 — forceAgent 강제 지정 (orchestrator와 독립적으로 존재)
if (lowerMsg.includes('보유') && (lowerMsg.includes('뉴스') || lowerMsg.includes('시장'))) {
  forceAgent = 'analysis';
} else if (lowerMsg.includes('포트폴리오') || lowerMsg.includes('내 주식') || ...) {
  forceAgent = 'portfolio';
}

// orchestrator.js — compound 조건 (같은 의도를 다르게 구현)
if (hasPortfolioKeyword && hasMarketKeyword) return 'analysis';
```

같은 compound 조건이 두 곳에 구현되어 있어 한 곳을 수정하면 다른 곳과 불일치가 생긴다.

### 1-2. 에이전트 간 중복 키워드

```js
// orchestrator.js ROUTING_RULES
{ agent: 'analysis', keywords: ['급등', '급락', '이유', '왜', '원인', '오늘 시장'] }
{ agent: 'alert',    keywords: ['급등', '급락', '관심종목', '오늘', '시장'] }
```

`'급등'`, `'급락'`은 analysis와 alert 양쪽에 존재한다. ROUTING_RULES 배열 순서상 analysis가 먼저 오기 때문에 "관심종목 급등 있어?" 같은 질문이 alert 대신 analysis로 라우팅된다.

### 1-3. 순서 의존성 — 배열 순서가 우선순위

```
현재 ROUTING_RULES 순서:
1. analysis  ← 먼저 검사
2. journal
3. portfolio
4. research
5. alert     ← 나중에 검사 (analysis에서 이미 걸림)
6. report
```

순서를 바꾸면 전체 라우팅 결과가 달라진다. 의도한 우선순위가 코드에 명시되지 않고 배열 위치에 암묵적으로 숨어 있다.

### 1-4. 구체적 오라우팅 사례

| 사용자 메시지 | 현재 결과 | 의도한 결과 | 원인 |
|---|---|---|---|
| "오늘 어때?" | portfolio (fallback) | alert | `'오늘'` 키워드 없음 |
| "관심종목 급등 있어?" | analysis | alert | 중복 키워드, analysis 우선 |
| "뉴스 뭐 있어?" | portfolio (fallback) | alert | 키워드 미매칭 |
| "내 포트폴리오 분석해줘" | analysis or portfolio | analysis | compound 조건 불일치 |
| "삼성전자 살까?" | research | research | 정상 (하지만 오타 시 깨짐) |
| "삼성전차 어때?" | portfolio (fallback) | research | 오타 처리 없음 |

### 1-5. fallback이 portfolio로 고정

키워드 미매칭 시 무조건 portfolio 에이전트로 떨어진다. 신규 사용자가 "안녕" 같은 인사를 보내도 portfolio 응답이 오는 부자연스러운 경험이 발생한다.

## 2. 개선 방향 비교

### Option A — 점수 기반 키워드 확장

**방법.** 각 에이전트에 가중치 키워드 목록을 두고, 가장 높은 점수의 에이전트를 선택한다.

```js
const SCORING_RULES = {
  analysis: { high: ['왜', '이유', '원인'], low: ['급등', '급락', '시장'] },
  alert:    { high: ['관심종목', '알림'],  low: ['급등', '급락', '오늘'] },
  ...
}
```

**장점.** 중복 키워드 충돌 해소, 추가 비용 없음.

**단점.** 가중치 수동 조정 필요, 오타·문맥 여전히 처리 불가, 복합 질문 취약.

### Option B — 전체 LLM 라우팅

**방법.** 모든 메시지를 Claude에게 에이전트 분류 요청 후 선택.

**장점.** 오타·문맥·복합 질문 완벽 처리, 키워드 관리 불필요.

**단점.** 모든 요청에 추가 API 호출 발생(~500ms 지연, 비용 증가). 단순 질문에도 과비용.

### Option C — 하이브리드 (권장)

**방법.** 고신뢰 규칙으로 먼저 처리하고, 모호한 경우에만 Claude Haiku로 분류.

```
메시지 입력
  ↓
scoreRouting() — 고신뢰 키워드 매칭
  ├─ 점수 70+ → 해당 에이전트 즉시 선택
  └─ 점수 미달 → classifyIntent() via Claude Haiku
                   ↓
               에이전트 선택
```

**장점.** 대부분(~70-80%)의 명확한 질문은 무비용 처리, 모호한 경우만 LLM 보조, 오타·문맥 처리 가능.

**단점.** classifyIntent 구현 필요, 모호한 케이스에서 ~300ms 추가 지연.

**선택 근거.** 비용과 정확도의 최적 균형점. Haiku는 토큰당 비용이 Sonnet의 1/10 수준이고 분류 작업에 충분한 성능을 보인다. 시스템 프롬프트에 Anthropic prompt cache(`cache_control: ephemeral`)를 적용하면 반복 호출 비용이 추가로 낮아진다.

## 3. Option C 상세 설계

### 3-1. 라우팅 로직 단일화

`AIChat.jsx`의 forceAgent 로직을 `orchestrator.js`로 통합한다. `AIChat.jsx`는 단순히 `routeToAgent(msg, context)`를 호출하기만 한다.

```js
// 변경 전: AIChat.jsx에 라우팅 판단 존재
let forceAgent = null;
if (lowerMsg.includes('보유') && ...) { forceAgent = 'analysis'; }
// ...
const result = await sendToAgent(msg, context, forceAgent);

// 변경 후: AIChat.jsx는 context만 전달
const result = await sendToAgent(msg, context);
// sendToAgent 내부에서 routeToAgent(msg, context) 호출
```

`routeToAgent`에 `context` 파라미터를 추가해 compound 조건 판단 시 보유종목 유무를 직접 확인한다.

### 3-2. 키워드 신뢰도 분리

각 에이전트 규칙을 `high`/`low` 두 계층으로 분리한다.

```js
const ROUTING_RULES = [
  {
    agent: 'analysis',
    high: ['왜', '이유', '원인', '급등한 이유', '급락한 이유'],
    low:  ['급등', '급락', '변동'],
  },
  {
    agent: 'journal',
    high: ['패턴', '심리', '일지', '매매 기록', '내 실수'],
    low:  ['기록', '분석'],
  },
  {
    agent: 'research',
    high: ['살까', '어때', '분석해줘', '리서치'],
    low:  ['전망', '목표가'],
  },
  {
    agent: 'portfolio',
    high: ['포트폴리오', '수익률', '내 종목', '평가금액'],
    low:  ['보유', '잔고'],
  },
  {
    agent: 'alert',
    high: ['관심종목', '알림', '오늘 시장', '모니터링'],
    low:  ['오늘', '뉴스'],
  },
  {
    agent: 'report',
    high: ['리포트', '성과', '결산', '월간', '주간'],
    low:  ['통계', '기간'],
  },
];
```

`high` 키워드 매칭 시 +30점, `low` 매칭 시 +10점. 70점 이상이면 즉시 선택.

### 3-3. scoreRouting() 구현

```js
function scoreRouting(msg, context) {
  const lower = msg.toLowerCase();
  const scores = {};

  // compound 조건 (기존 로직 통합)
  const hasHoldings = context?.holdings?.length > 0;
  const hasPortfolioKw = ['포트폴리오', '내 주식', '내 자산', '보유'].some(k => lower.includes(k));
  const hasMarketKw = ['뉴스', '시장', '지수'].some(k => lower.includes(k));
  if (hasHoldings && hasPortfolioKw && hasMarketKw) {
    return { agent: 'analysis', score: 100, method: 'compound' };
  }

  for (const rule of ROUTING_RULES) {
    let score = 0;
    for (const kw of rule.high) { if (lower.includes(kw)) score += 30; }
    for (const kw of rule.low)  { if (lower.includes(kw)) score += 10; }
    if (score > 0) scores[rule.agent] = (scores[rule.agent] || 0) + score;
  }

  const best = Object.entries(scores).sort((a, b) => b[1] - a[1])[0];
  if (best && best[1] >= 70) {
    return { agent: best[0], score: best[1], method: 'keyword' };
  }

  return null; // 모호 → classifyIntent로 위임
}
```

### 3-4. 3단계 라우팅 흐름

```
routeToAgent(msg, context)
  │
  ├─① compound 조건 체크 (보유종목 + 시장 키워드 → analysis)
  │
  ├─② scoreRouting() — 고신뢰 키워드 점수
  │     ├─ 70점 이상 → 해당 에이전트 반환
  │     └─ 미달      → 다음 단계
  │
  └─③ classifyIntent() — Claude Haiku 호출
        ├─ 분류 성공 → 해당 에이전트 반환
        └─ 실패/오류 → 'portfolio' fallback
```

### 3-5. classifyIntent 프롬프트 설계

```js
const CLASSIFY_SYSTEM = `당신은 투자 앱의 라우터입니다.
사용자 메시지를 읽고 아래 에이전트 중 하나를 선택해 JSON으로 반환하세요.

에이전트 목록:
- analysis: 보유 포트폴리오와 시장 이벤트 연관 분석, 종목 급등락 원인
- journal: 매매 심리 패턴 분석, 실수 회고, 일지 코칭
- research: 특정 종목 탐색, 매수 검토, 기업 분석
- portfolio: 보유 종목 현황, 수익률, 비중 조회
- alert: 관심종목 모니터링, 오늘 시장 동향, 뉴스 스캔
- report: 기간별 성과 리포트, 결산, 벤치마크 비교

출력 형식: {"agent": "<에이전트명>"}`;

async function classifyIntent(msg) {
  const res = await fetch('/api/claude', {
    method: 'POST',
    body: JSON.stringify({
      model: 'claude-haiku-4-5-20251001',
      max_tokens: 50,
      system: [{ type: 'text', text: CLASSIFY_SYSTEM,
                  cache_control: { type: 'ephemeral' } }],
      messages: [{ role: 'user', content: msg }],
    }),
  });
  const { agent } = JSON.parse(res.choices[0].text);
  return VALID_AGENTS.includes(agent) ? agent : 'portfolio';
}
```

`cache_control: ephemeral`을 시스템 프롬프트에 적용해 Anthropic 측 캐시를 활용한다. 동일한 시스템 프롬프트를 반복 전송할 때 첫 번째 호출 이후 캐시 히트 비용(입력 토큰의 10%)으로 절감된다.

## 7. 고려 사항

### 비용

- Phase 1만 적용 시 추가 비용 없음.
- Phase 2: classifyIntent는 max_tokens=50, 입력~200토큰 수준. Haiku 가격 기준 1,000회 호출당 약 $0.02(입력) + $0.01(출력). prompt cache 적용 시 입력 비용 ~90% 절감.
- 전체 요청의 20-30%만 Haiku를 거친다고 가정하면 일일 사용량 100회 기준 월 $0.1 미만.

### 지연

- scoreRouting() 자체는 동기 함수 — 추가 지연 없음.
- classifyIntent 호출 시 약 200-400ms 추가. 명확한 질문은 영향 없음.
- 필요 시 classifyIntent를 타임아웃 300ms로 감싸고, 초과 시 'portfolio' fallback 적용.

### 확장성

- 에이전트를 추가할 때 `ROUTING_RULES`에 항목 하나와 `CLASSIFY_SYSTEM`의 에이전트 목록 한 줄만 추가하면 된다.
- 현재처럼 배열 순서를 바꿔가며 우선순위를 맞출 필요 없음.

### 롤백

- Phase 1은 기존 키워드 배열을 재구성한 것이므로 git revert 한 줄로 즉시 되돌릴 수 있다.
- Phase 2는 classifyIntent가 실패해도 fallback이 있어 기능 저하 없이 롤백 가능.
