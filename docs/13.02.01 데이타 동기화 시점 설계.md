## 1. 설계 배경 및 목표

### 1.1 현행 동기화 시점의 공백

현재 `syncService.uploadAll()`은 다음 두 시점에만 실행된다.

| 시점 | 방식 |
|------|------|
| 타이머 인터벌 (15분/1시간) | `setInterval` → `uploadAll()` |
| 수동 클릭 | 설정 화면 "서버에 업로드" 버튼 |

**공백 1 — 앱 종료 시 미업로드.** 타이머 사이에 데이터를 입력하고 탭을 닫으면 그 변경분은 서버에 저장되지 않는다.

**공백 2 — 재로그인 기기의 증분 다운로드.** `transactions.count() === 0` 조건만 보므로, 데이터가 일부라도 있는 기기(재로그인, 공용 PC 등)에서는 서버의 최신 변경분을 받지 못한다.

### 1.2 이번 설계 범위

| 번호 | 기능 | 설명 |
|------|------|------|
| S-1 | 앱 종료/이탈 시 미동기화 업로드 | 대기 레코드 있으면 팝업 → 업로드 → 완료/오류 메시지 |
| S-2 | 로그인 후 증분 다운로드 | `lastSyncedAt` 기준으로 서버 변경분만 받아 병합, 토스트 알림 |

## 2. S-1: 앱 종료/이탈 시 미동기화 업로드

### 2.1 트리거 정의

| 이벤트 | 처리 방식 |
|--------|----------|
| 앱 내 페이지 이동 (React Router) | `usePendingSync` 훅 → 커스텀 모달 표시 |
| 브라우저 탭 닫기 / 새로고침 / 주소 이탈 | `beforeunload` 이벤트 → 브라우저 기본 확인창 + `pagehide` 백그라운드 업로드 |

**앱 내 이동과 브라우저 이탈을 분리하는 이유.** `beforeunload`에서는 DOM 조작이 불가능하므로 커스텀 팝업을 보여줄 수 없다. React Router 내 이동은 앱이 살아있으므로 커스텀 모달을 정상적으로 표시할 수 있다.

### 2.2 대기 레코드 감지

미동기화 레코드는 `SYNC_TABLE_MAP` 전체 테이블에서 `syncedAt === null` 인 레코드의 총합으로 정의한다.

```javascript
// src/services/syncService.js 에 추가
async countPendingRecords() {
  let total = 0
  for (const { local } of SYNC_TABLE_MAP) {
    if (!db[local]) continue
    const count = await db[local].filter(r => !r.syncedAt).count()
    total += count
  }
  return total
}
```

### 2.3 앱 내 페이지 이동 처리 흐름

```
사용자가 다른 페이지로 이동 시도
  ↓
usePendingSync 훅 — countPendingRecords() 실행
  ↓
  ├─ 0건 → 이동 허용 (팝업 없음)
  └─ 1건 이상 → PendingUploadModal 표시
       ↓
       [업로드 후 이동] 버튼
         → 업로드 시작 (로딩 스피너 표시)
         → 성공: "N개 항목이 서버에 저장되었습니다." 토스트 → 이동
         → 실패: 오류 사유 표시 + [그냥 이동] / [재시도] 버튼
       [그냥 이동] 버튼
         → 업로드 없이 이동 (데이터는 로컬 IDB에 보존됨)
       [취소] 버튼
         → 이동 취소, 현재 페이지 유지
```

### 2.4 PendingUploadModal 명세

| 항목 | 내용 |
|------|------|
| 파일 위치 | `src/components/sync/PendingUploadModal.jsx` |
| 트리거 | `usePendingSync` 훅에서 pendingCount > 0 감지 시 |
| 표시 내용 | "서버에 저장되지 않은 변경사항이 N개 있습니다." |
| 버튼 | 업로드 후 이동 / 그냥 이동 / 취소 |
| 업로드 중 상태 | 버튼 비활성화 + 스피너 + "업로드 중..." 텍스트 |
| 업로드 성공 | 모달 닫힘 + 성공 토스트 + 페이지 이동 |
| 업로드 실패 | 오류 메시지 인라인 표시 + 버튼 재활성화 |

**업로드 실패 시 오류 메시지 예시.**
```
서버 업로드에 실패했습니다.
원인: 네트워크 연결을 확인해 주세요. (HTTP 503)

변경사항은 이 기기의 로컬 저장소에 보존되어 있습니다.
다음 자동 동기화(최대 15분 후) 또는 설정 → 동기화에서 수동으로 재시도할 수 있습니다.
```

### 2.5 브라우저 탭 닫기 / 이탈 처리

브라우저의 `beforeunload` 이벤트는 커스텀 DOM UI를 허용하지 않으므로 다음 두 단계로 처리한다.

**단계 1 — 브라우저 기본 확인창 표시.**
```javascript
// src/hooks/useBeforeUnloadSync.js
window.addEventListener('beforeunload', (event) => {
  const pendingCount = useSyncStore.getState().pendingChanges
  if (pendingCount > 0) {
    event.preventDefault()
    event.returnValue = ''  // 브라우저 기본 "페이지에서 나가시겠습니까?" 창 표시
  }
})
```

**단계 2 — `pagehide` 이벤트에서 백그라운드 업로드 시도.**
```javascript
window.addEventListener('pagehide', () => {
  const pendingCount = useSyncStore.getState().pendingChanges
  if (pendingCount === 0) return

  // navigator.sendBeacon: 페이지 언로드 후에도 요청 완료를 보장
  // 단, 응답을 받을 수 없으므로 완료 확인 불가 — 보조 수단으로만 사용
  const token = authService.getCachedToken()
  if (token) {
    navigator.sendBeacon('/api/sync/upload-pending', JSON.stringify({ token }))
  }
})
```

**pagehide 백그라운드 업로드의 제약.**
- 응답 수신 불가 → 성공/실패 확인 불가
- 페이로드 크기 제한 (64KB 미만 권장)
- 보조 수단으로만 사용, 주 흐름은 모달 경유

### 2.6 `pendingChanges` 카운터 관리

`syncStore.pendingChanges`를 데이터 변경 시 자동으로 증가시켜 모달 표시 여부 결정에 사용한다.

| 이벤트 | 액션 |
|--------|------|
| 스토어에서 데이터 추가/수정/삭제 | `incrementPending()` |
| `uploadAll()` 성공 완료 | `resetPending()` |
| 앱 초기화 시 | `countPendingRecords()` 결과로 초기값 설정 |

## 3. S-2: 로그인 후 증분 다운로드

### 3.1 현행 문제

```javascript
// 현재 App.jsx L120~126
const txCount = await idb.transactions.count()
if (txCount === 0) {
  syncService.downloadAndReload(session.user.id)  // 전체 다운로드
}
```

`transactions`가 1개라도 있으면 다운로드를 건너뛴다. 다른 기기에서 새 데이터를 추가한 후 이 기기에서 재로그인해도 반영되지 않는다.

### 3.2 증분 다운로드 전략

`lastSyncedAt` 기준 델타 다운로드를 사용한다. 서버에 `?since=<ISO 타임스탬프>` 파라미터를 전달하면 해당 시각 이후에 `synced_at`이 업데이트된 레코드만 반환한다. `api/sync/download.js`에는 이미 `since` 파라미터 처리 로직이 존재한다 (13.01.01 §6.2 참조).

```
로그인 완료
  ↓
syncStore.lastSyncedAt 조회
  ↓
  ├─ null → downloadAll() 전체 다운로드 (최초 기기)
  └─ 값 있음 → downloadAllDelta(since = lastSyncedAt - 5분) 증분 다운로드
  ↓
총 다운로드 건수 집계
  ↓
  ├─ 0건 → 토스트 없음 (조용히 완료)
  └─ 1건 이상 → 토스트 표시
  ↓
Zustand 스토어 재로드
```

**`since`를 5분 이전으로 설정하는 이유.** `lastSyncedAt`은 업로드 완료 시에도 갱신된다. 다른 기기에서 이 기기 업로드 직후에 데이터를 추가했다면, 그 레코드의 `synced_at`이 `lastSyncedAt`보다 약간 이전일 수 있다. 5분 마진을 두면 이런 경계 케이스를 커버할 수 있다. `bulkPut`은 멱등 연산이므로 중복 수신은 무해하다.

### 3.3 신규 함수 명세

**`downloadTable(localTable, since)`** — 기존 함수에 `since` 파라미터 추가.
```javascript
async downloadTable(localTable, since = null) {
  // ...
  const qs = since
    ? `table=${localTable}&since=${encodeURIComponent(since)}`
    : `table=${localTable}`
  const res = await fetch(`${API_BASE}/api/sync/download?${qs}`, { ... })
  // ...
}
```

**`downloadAllDelta(since)`** — 증분 전체 테이블 다운로드.
```javascript
async downloadAllDelta(since) {
  const { setSyncStatus, setLastSyncedAt } = useSyncStore.getState()
  setSyncStatus('syncing')
  try {
    let total = 0
    for (const { local } of SYNC_TABLE_MAP) {
      if (!db[local]) continue
      const { downloaded } = await syncService.downloadTable(local, since)
      total += downloaded
    }
    setLastSyncedAt(new Date().toISOString())
    setSyncStatus('synced')
    return { total }
  } catch (err) {
    setSyncStatus('error')
    throw err
  }
}
```

**`downloadDeltaAndReload(userId, since)`** — 증분 다운로드 + 스토어 재로드.
```javascript
async downloadDeltaAndReload(userId, since) {
  const { total } = await syncService.downloadAllDelta(since)
  if (total === 0 || !userId) return { total }
  // 기존 downloadAndReload 의 스토어 재로드 로직 동일하게 실행
  await Promise.all([
    useAccountStore.getState().loadFromDB(userId),
    useJournalStore.getState().loadFromDB(userId),
    useCashFlowStore.getState().loadFromDB(userId),
    useWatchlistStore.getState().loadFromDB(userId),
    useDailyPnlStore.getState().loadFromDB(userId),
  ])
  return { total }
}
```

### 3.4 App.jsx 로그인 후 처리 변경

**현행:**
```javascript
const txCount = await idb.transactions.count()
if (txCount === 0) {
  syncService.downloadAndReload(session.user.id).catch(...)
}
```

**변경 후:**
```javascript
const { lastSyncedAt } = useSyncStore.getState()
const fiveMinAgo = lastSyncedAt
  ? new Date(new Date(lastSyncedAt).getTime() - 5 * 60 * 1000).toISOString()
  : null

if (!fiveMinAgo) {
  // 최초 기기 — 전체 다운로드
  syncService.downloadAndReload(session.user.id)
    .then(({ total }) => {
      if (total > 0) toast.success(`서버에서 ${total}개 항목을 받아왔습니다.`)
    })
    .catch(err => console.warn('[Sync] 자동 다운로드 실패:', err))
} else {
  // 기존 기기 재로그인 — 증분 다운로드
  syncService.downloadDeltaAndReload(session.user.id, fiveMinAgo)
    .then(({ total }) => {
      if (total > 0) toast.info(`서버에서 ${total}개 변경사항을 받아왔습니다.`)
    })
    .catch(err => console.warn('[Sync] 증분 다운로드 실패:', err))
}
```

### 3.5 토스트 메시지 명세

| 상황 | 타입 | 메시지 |
|------|------|--------|
| 전체 다운로드 성공 (N > 0) | success | "서버에서 N개 항목을 받아왔습니다." |
| 증분 다운로드 성공 (N > 0) | info | "서버에서 N개 변경사항을 받아왔습니다." |
| 다운로드 성공 (0건) | 표시 안 함 | — |
| 다운로드 실패 | warning | "서버 동기화에 실패했습니다. 로컬 데이터로 계속합니다." |

## 5. 설계 결정 및 트레이드오프

### 5.1 `beforeunload` 에서 커스텀 팝업 불가

현대 브라우저는 보안 정책상 `beforeunload` 핸들러에서 `alert`, `confirm`, DOM 조작을 차단한다. React Router 내 이동에서만 커스텀 모달을 표시하고, 탭 닫기/외부 URL 이탈은 브라우저 기본 확인창 + `pagehide` 백그라운드 업로드로 처리한다.

### 5.2 오프라인 상태 처리

업로드 실패 시 데이터는 IDB에 `syncedAt=null`로 보존되어 손실이 없다. 오류 메시지에서 "로컬에 보존됨"을 명확히 안내하여 사용자가 데이터 손실을 우려하지 않도록 한다.

### 5.3 `pendingChanges` 카운터 정확도

각 스토어에서 `incrementPending()`을 호출하지 않으면 카운터가 부정확해진다. 앱 초기화 시 `countPendingRecords()` 로 IDB를 실제 스캔하여 보정하므로, 카운터 누락이 있어도 앱 재시작 후에는 정확해진다.
